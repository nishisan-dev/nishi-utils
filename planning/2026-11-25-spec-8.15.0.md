## 2. Item A — R1(a): rota removida no fechamento e definição internada

### 2.1 Problema
- `WriteDispatcher.routes` cresce para sempre. Cada série escrita deixa uma `SeriesRoute`, com lock, condition,
  2 deques e 2 sets, que nem `close()` remove. Com séries mudando de cliente (rebalance de partições), a memória
  cresce sem limite.
- Cada handle novo refaz SHA-256, parse do YAML e `GeometryDescriptor`. Cada `open()`, mesmo em cache, refaz outro
  parse para achar o template da chave.

### 2.2 Estado atual
- `routes` em `cl/client/WriteDispatcher.java:145`; criação em `enqueue` (`:366`) e `beginGeneration` (`:201-229`).
  Não existe `routes.remove`.
- `SeriesRoute` em `:1518-1584`. `isIdle` em `:1269-1272`: no modo `BARRIER`, uma falha mantém a rota no índice
  "até o restart" (`:1227-1229`), para que um checkpoint posterior não certifique um prefixo perdido.
- `RemoteSeriesHandle.close(Duration)` (`cl/client/RemoteSeriesHandle.java:525-554`): faz flush, `CLOSE` remoto e
  `onClose`, mas não avisa o dispatcher.
- Parse em `cl/client/DefaultNgrrdClusterClient.java:327` e `:463-477`.

### 2.3 Desenho

**A.1 Rota com dono (holders).** Uma rota passa a saber quais handles a usam.
- O `WriteBuffer` ganha métodos `default` (pacote `client`, interno):
  ```java
  default void beginGeneration(String key, String generation, String owner, Object holder) {
      beginGeneration(key, generation, owner);
  }
  /** O holder deixou de usar a rota; rota sem holder e ociosa sai do mapa. */
  default void endGeneration(String key, String generation, Object holder) { }
  ```
- O `SeriesRoute` ganha `Set<Object> holders` (identidade; normalmente um elemento). Ele só muda sob `route.lock`.
  - `beginGeneration` com a mesma geração adiciona o holder. Uma reabertura (`reopen`) do mesmo handle é
    idempotente, porque é o mesmo objeto.
  - Com uma geração diferente, o comportamento de hoje se mantém: a rota antiga é aposentada e a nova nasce com
    `{holder}`.
- `RemoteSeriesHandle` passa `this` como holder em `open` (`:267`). Chama `endGeneration` em todo caminho que leva
  o handle a fechado: `close(Duration)` depois do flush/CLOSE, `discard()`, `markTerminal(...)` e no fim de `release`
  (item B).
- **Regra de remoção** (método privado `removeIfRetired(route)`, sempre sob `route.lock`):
  `holders.isEmpty() && isIdle(route) && waiters.isEmpty() && !redirectPending && !ownerLookupPending`
  → `routes.remove(key, route)`, `pendingRoutes.remove(route)`, `lastRetryLogMs.remove(key)` e, sob o `buf.lock` de
  cada `NodeBuffer`, `queue.forgetAttempts(key)`.
- **Onde a regra é avaliada:**
  - em `endGeneration`;
  - em `completeWrites`, quando a rota fica ociosa;
  - em `mark()` e `releaseWaiters`, quando uma marca colhe as falhas e a rota fica ociosa;
  - em `applyOwnerLookup` e `releaseWithoutLookup`, ao limpar `ownerLookupPending`.

  Assim, "remover quando fica ociosa" cobre a rota que fecha com escrita em voo: ela sai quando a última resposta
  chega.
- **Garantias preservadas:**
  - **BARRIER:** uma rota com falha não fica ociosa (`isIdle` exige `firstFailedSequence == MAX`), então continua no
    mapa como hoje. Só `release` (item B) a remove, depois de entregar a falha ao chamador.
  - **MARKS:** uma rota com falha não reportada continua no mapa até uma marca colhê-la. Depois disso, ela sai.
  - Todo caminho que hoje faz `routes.get(key) != route` → no-op continua correto. Uma rota removida é tratada como
    "geração aposentada", e só uma rota sem escrita em voo pode ser removida.
- **Rota criada por `enqueue` sem holder** (`:366`, `computeIfAbsent`): isso só acontece se um handle aberto
  escrever depois de a rota dele sumir, o que a regra impede. A rota fica sem holder e sai quando ficar ociosa.
  Funciona, com um custo pequeno de recriação. O teste cobre esse caso.
- **`close()` do dispatcher:** não muda (o processo vai embora).

**A.2 Definição internada no cliente.** Nova classe `cl/client/DefinitionInterner.java` (package-private):
```java
record InternedDefinition(String yaml, String hashHex, GeometryDescriptor geometry,
                          String definitionName, String seriesKeyTemplate) { }

final class DefinitionInterner {
    static final int MAX_ENTRIES = 4096;
    InternedDefinition intern(String yaml);   // chave = conteúdo do YAML
    int size();
}
```
- O mapa é `ConcurrentHashMap<String, InternedDefinition>`, com o próprio conteúdo do YAML como chave.
  - Com a mesma instância de `String`, o custo é o `hashCode` em cache mais uma comparação por identidade.
  - Com instâncias diferentes de mesmo conteúdo, o custo é O(tamanho), ainda muito abaixo de SHA-256 + parse.
- **Na falta:** faz parse (`NgrrdYamlLoader.parse(yaml, System::getenv)`), hash, `GeometryDescriptor` e template, e
  publica com `putIfAbsent`. Devolve sempre a instância publicada, cujo `yaml` é a `String` canônica que todos os
  handles passam a referenciar. Isso corrige o caso de ~4,8 KB por handle com uma `String` por série.
- **Teto:** acima de `MAX_ENTRIES`, calcula sem publicar (o comportamento de hoje) e conta em `definitionsNotInterned`.
  O teto existe só contra uma definição gerada por série. O caso normal é de 10 definições.
- **Interpolação de ambiente:** o `System.getenv` é imutável durante o processo, então internar pelo texto bruto é
  equivalente ao que existe hoje.
- **Uso:**
  - `DefaultNgrrdClusterClient.open` (`:327`) troca `templateOf` por `interner.intern(yaml).seriesKeyTemplate()`;
  - `openNewHandle` (`:463-477`) recebe o `InternedDefinition` e repassa `yaml`, `hashHex`, `geometry` e `definitionName`
    ao `RemoteSeriesHandle`, cuja assinatura de construtor não muda.

**A.3 Métricas novas (cliente)** — componentes novos de `ClientMetricsSnapshot` (seção 9.2):
`routes` (gauge `routes.size()`), `routesRemoved` (contador) e `internedDefinitions` (gauge).

### 2.4 Contrato e compatibilidade
Só o cliente muda. Não há API pública nova além dos campos de métrica. `WriteBuffer` é público, mas os métodos novos
são `default`, então implementações de teste antigas continuam compilando.

  que já existe (`:396-400`, `:1247-1252`). Ela nunca toma `markLock` sob `route.lock`.

## 3. Item B — R2(a): `release(seriesKeys)` e protocolo de entrega

### 3.1 Problema
Com vários clientes escritores e partições que mudam de dono, o cliente que perde uma partição precisa de uma forma
de "entregar" as séries daquela partição. Ele precisa saber que tudo o que admitiu teve resposta final do dono antes
de confirmar o offset. Hoje só existe o `handle.close()` por série, que engole a falha de flush
(`cl/client/RemoteSeriesHandle.java:537-539`) e manda um `CLOSE` remoto que fecha a série no nó para **todos** os
clientes (`cl/node/StorageRequestHandler.java:837-840` → `registry.close`, que descarta a definição).

### 3.2 API pública (`cl/api/`)
```java
// NgrrdClusterClient
default CompletableFuture<ReleaseResult> release(Collection<String> seriesKeys) {
    return release(seriesKeys, ReleaseOptions.defaults());
}
default CompletableFuture<ReleaseResult> release(Collection<String> seriesKeys, ReleaseOptions options) {
    return CompletableFuture.failedFuture(new UnsupportedOperationException("release"));
}

public record ReleaseOptions(boolean checkpoint, boolean closeOnNode, Duration timeout, int maxConcurrentPerNode) {
    /** checkpoint=false, closeOnNode=false, timeout=null (= closeTimeout do cliente), maxConcurrentPerNode=32. */
    public static ReleaseOptions defaults();
    public ReleaseOptions withCheckpoint(boolean v);
    public ReleaseOptions withCloseOnNode(boolean v);
    public ReleaseOptions withTimeout(Duration v);
    public ReleaseOptions withMaxConcurrentPerNode(int v);   // >= 1
}

public enum ReleaseStatus {
    RELEASED,            // toda escrita admitida antes do release teve OK final do dono (e checkpoint, se pedido)
    NOT_HELD,            // este cliente não tinha handle nem rota da série: nada a fazer
    WRITE_FAILURES,      // drenou, mas há escritas com falha final ainda não reportadas a uma marca
    CHECKPOINT_FAILED,   // escritas OK; o CHECKPOINT pedido falhou ou estourou o prazo
    TIMED_OUT,           // o dreno não terminou no prazo (ver semântica abaixo)
    SERIES_DELETED       // a geração foi removida ou posta em quarentena durante o release
}

public record SeriesRelease(ReleaseStatus status, Map<SeriesStatus, Long> failedSamplesByStatus,
                            ErrorCode errorCode, String message) { }

public record ReleaseResult(Map<String, SeriesRelease> series) {
    public boolean allReleased();      // todos RELEASED ou NOT_HELD
    public Set<String> notReleased();
    public long failedSamples();
}
```

### 3.3 Semântica
1. **Admissão encerrada.** Para cada chave, sob o lock de abertura da chave em `SeriesHandleCache`
   (`openLocks` + `CoordinationLocks`):
   - o handle principal, gravável ou somente leitura, é tirado do mapa (`remove(key, handle)`) e levado a fechado
     localmente (`closeLocally`);
   - um `write` concorrente nesse handle lança `CLOSED`, porque o contrato pede que o chamador pare de escrever antes
     de chamar o `release`;
   - um `open()` posterior da mesma chave cria um handle novo, como hoje.
2. **Dreno.** `WriteDispatcher.drainForRelease(keys, deadline)` é um método novo, interno.
   - Fotografa `boundary = route.submitted` de cada rota e espera `completed >= boundary`, como `awaitBarriers`, mas
     **sem lançar**. Devolve um desfecho por chave.
   - Ao terminar o dreno de uma rota, sob `route.lock`:
     - **MARKS:** colhe as faixas de `unreportedFailures` até `boundary` para o resultado, contadas por status. Elas
       deixam de ir para uma marca, então cada falha é reportada uma única vez, à marca ou ao `release`.
     - **BARRIER:** se `firstFailedSequence <= boundary`, o resultado é `WRITE_FAILURES`, com a mensagem.
     - Em ambos, `failureCode` `SERIES_DELETED`/`QUARANTINED` → `SERIES_DELETED`.
3. **Checkpoint opcional** (`checkpoint=true`): só para as chaves sem falha de escrita. Usa o `CHECKPOINT` existente
   (`executeSeriesCommand`, com `OperationRetry` limitado ao prazo do release, um construtor novo com `deadlineMs`
   explícito). Falha ou prazo → `CHECKPOINT_FAILED`.
4. **`CLOSE` no nó opcional** (`closeOnNode=true`): o `CLOSE` existente, com a mesma regra de orçamento e conexão de
   `close(Duration)`. Uma falha só vai para o log (WARNING), igual a hoje. O **padrão é não mandar**, por dois motivos:
   - na entrega, o próximo dono vai reabrir a mesma série no mesmo nó, e o `CLOSE` faria o nó fazer
     checkpoint + close + reopen à toa;
   - pior, o `CLOSE` descarta a definição no nó (`registry.close`). Se o outro cliente já tiver aberto a série,
     cada escrita dele passa a receber `NOT_OPEN` e paga um OPEN.

   Série abandonada de vez fecha pela ociosidade do nó, com a definição ainda em cache. `closeOnNode=true` é para
   desativação planejada.
5. **Limpeza local:**
   - `endGeneration(key, generation, handle)`;
   - para `RELEASED`, `WRITE_FAILURES`, `CHECKPOINT_FAILED` e `SERIES_DELETED`, a remoção é **forçada**: a falha já
     foi entregue ao chamador, então a rota sai mesmo em BARRIER, desde que `completed == submitted` e nenhum outro
     holder tenha se ligado nesse meio-tempo;
   - `resolver.invalidate(key)` (remove `PlacementResolver.overrides`).
6. **`TIMED_OUT`:** o handle já está fechado e a rota fica sem holder.
   - As escritas pendentes continuam sendo entregues em segundo plano.
   - A rota sai quando ficar ociosa (regra A.1). Falhas que surgirem depois vão para a próxima marca (MARKS) ou
     ficam na rota (BARRIER), como hoje.
   - O chamador **não** deve confirmar o offset dessas séries.
7. **Execução:**
   - o release roda num executor de virtual threads (`ngrrd-release-`);
   - as RPCs de `CHECKPOINT`/`CLOSE` são limitadas por `maxConcurrentPerNode` (um `Semaphore` por dono);
   - o prazo total é `timeout` (padrão `closeTimeout`, 30 s) e vale para o dreno + checkpoint + close;
   - a future nunca falha por causa de uma série. Ela só falha com `CLOSED` (cliente fechado) ou se `seriesKeys`
     for nulo.
8. **Durabilidade:** sem `checkpoint`, a garantia é a mesma de uma marca: ACK do dono, sem fsync. Com `checkpoint`,
   é fsync confirmado no dono.

### 3.4 Protocolo de entrega entre clientes (entra na doc)
Para consumidores particionados, Kafka ou equivalente, com séries particionadas de forma disjunta entre clientes:

```
Cliente A (perde P)                              Cliente B (ganha P)
onPartitionsRevoked(P)
  1. para de chamar write() nas séries de P
  2. r = client.release(séries de P[, opts]).join()
  3. se r.allReleased(): commit do offset de P
     senão: não confirma (ou confirma até a última
            marca concluída sem falha) e loga
            r.notReleased()
                                                 onPartitionsAssigned(P)
                                                  4. open() das séries de P (sob demanda)
                                                  5. retoma a partir do offset confirmado
```

- **Ordem garantida pelo grupo:** no protocolo *eager* e no *cooperative*, a atribuição de P a B só acontece depois
  de o callback de revogação de A terminar. O `release` tem que caber nesse callback. A regra é `timeout` menor que
  o prazo do grupo (`max.poll.interval.ms` ou equivalente), com folga.
- **Zumbi:** se A estourar o prazo e o grupo reatribuir P, A e B podem escrever ao mesmo tempo, e vale "último
  escritor vence". A proteção contra isso é a cerca por `writerEpoch`/`FENCED` da 8.16 (R2(b)). A doc da 8.15 deixa
  esse limite explícito.
- **Reescrita depois do offset:** B reprocessa a partir do offset confirmado. Amostras que A já tinha gravado depois
  desse offset são reescritas. Com o mesmo timestamp, a engine segue a `lateSamplePolicy`. A doc explica isso.
- **Sem `release`:** o comportamento continua o de hoje, funcional mas sem garantia de fronteira e com vazamento de
  rota (que o item A corrige).

### 3.5 Contrato e compatibilidade
- API nova, só no cliente, com métodos `default` na interface. Nenhum comando novo.
- Usa `CHECKPOINT` e `CLOSE`, que existem desde sempre. Funciona contra nós 8.14.2.

  - `releaseDeCemMilSeriesNaoBloqueiaThreadDoChamador` (future, virtual threads; tempo limitado).
- **Cluster (`-Pngrrd-cluster`)**, nova `ReleaseHandoverClusterTest` com 3 storages e 2 clientes:
  - A escreve continuamente em 2 mil séries;
  - em seguida faz `release(...).join()` e deve receber `allReleased()`;
  - B abre as mesmas séries e continua;
  - asserções: nenhuma amostra perdida na leitura final, zero `NOT_OPEN` no nó com o padrão
    (`closeOnNode=false`), e `routes == 0` em A.
  - Uma variação com `closeOnNode=true` verifica que o `NOT_OPEN` de B (se B abriu antes) é autocurado.

### 3.7 Riscos
- **Release com milhões de séries numa partição única** (o cenário de hoje tem uma partição). Sem
  `checkpoint`/`closeOnNode`, o custo é local: dreno e limpeza, sem RPC por série. Com `checkpoint=true`, é uma RPC
  por série. A doc recomenda `checkpoint=false` e confia no checkpoint local do nó (8.14) para a durabilidade.
- **Corrida com `open()` da mesma chave no mesmo processo.** É coberta pelo lock de abertura e pela regra de holders.
- **Uma marca já aberta esperando uma rota que é liberada.** O dreno conclui os waiters antes da colheita, e a ordem
  das marcas se mantém, porque a colheita do release só pega falhas **depois** da fronteira de cada waiter já
  liberado.

## 4. Item C — R4(a)(b): fill sobre a capacidade declarada, limiares e crescimento do shard

### 4.1 Problema
- **Doc errada.** `doc/oss/ngrrd-blob-volume.md` §8 (linhas 191-196) promete *linear probing* para outro shard. O
  código usa sempre o shard de `BlobRouting.shardFor` (`oss/storage/blob/BlobStorage.java:416`) e **cresce** esse
  shard (`allocateInShard`, `:431-447`).
- **`maxFillRatio` engana o alerta.** É o fill por shard sobre o tamanho **atual** do arquivo: anda em dente de serra
  e fica perto de 1,0 normalmente. O alerta que importa é sobre a capacidade declarada.
- **Crescimento sem medida.** O crescimento roda sob `structuralLock` e bloqueia toda criação no volume. Não existe
  métrica do tempo que ele leva.

### 4.2 Desenho

## 5. Item D — R7(a): force fora do writer, índice de séries sujas, `spreadFraction` e métricas

### 5.1 Problema
- **Disputa com a ingestão.** O force (msync/fdatasync) de cada checkpoint roda na thread do `ngrrd-writer-pool`
  (`max(2, nCPU)` threads, `oss/writer/WriterScheduler.java:46`), que é a mesma da ingestão. Com `maxInFlight` alto,
  os forces ocupam as threads de escrita.
- **Varredura completa.** O ciclo de checkpoint local varre o registry inteiro para achar as sujas
  (`cl/node/SeriesHandleRegistry.java:342-348`), e o tick de status faz o mesmo para `dirtyCount()` (D7).
- **Sem alavanca nem medida.** A fração de espalhamento é fixa (`SPREAD_FRACTION = 0.8`,
  `cl/node/LocalCheckpointer.java:78`). Não existe medida de espera em fila nem de duração do force.

### 5.2 Desenho

**D.1 Force destacável (`oss`).**
- **`SeriesChannel`** (`oss/storage/SeriesChannel.java`) ganha:
  ```java
  /** Prepara o force: captura o que precisa ser forçado e limpa a marca de sujo. Chamado só pela thread do writer. */
  default ForceTicket prepareForce() { force(); return ForceTicket.DONE; }

  interface ForceTicket {
      ForceTicket DONE = () -> { };
      /** Executa o force capturado; pode rodar em outra thread. Em falha, a implementação volta a marcar o canal como sujo. */
      void run();
      default boolean detached() { return this != DONE; }
  }
  ```
  - O padrão (S3, disco local) faz o force inline como hoje e devolve `DONE`. O S3 nunca sai da thread do writer,
    porque o PUT relê a imagem em memória.
- **`BlobSeriesChannel`** (`oss/storage/blob/BlobSeriesChannel.java:68-74`):
  - o campo `dirty` passa a ser `volatile`;
  - `prepareForce()`: se `shard == null || !dirty`, devolve `DONE`. Senão faz `dirty = false` e devolve um ticket
    que chama `shard.forceRange(baseOffset, length)` e, em exceção, faz `dirty = true` e relança;
  - `force()` continua igual, para close e Shutdown.
  - Forces concorrentes da mesma faixa já acontecem hoje entre séries do mesmo shard, e o msync é idempotente.
- **`NgrrdWriter`:**
  - `Command.Sync` passa a carregar `enqueuedNanos` e um `TimingSink` opcional (record `CheckpointTiming`, abaixo).
  - Fase A (thread do writer, igual a hoje até o `channel.force()`, `:774-799`): emite os CDPs parciais,
    `persistLiveState`, e chama `ticket = channel.prepareForce()`.
  - Se `forceExecutor == null` ou `!ticket.detached()`: segue inline, exatamente como hoje.
  - Senão:
    - `changedSinceForce = false`;
    - `inFlightForce = new CompletableFuture<>()`;
    - submete ao `forceExecutor` uma tarefa que roda `ticket.run()`, mede `forceNanos` e conclui `inFlightForce` e
      a future do Sync.
    - Em falha, enfileira `Command.ForceFailed`, que na thread do writer faz `changedSinceForce = true`, e conclui as
      futures com a exceção.
  - **Sync coalescido** (`!changedSinceForce`): se houver `inFlightForce` não concluída, a future do Sync é
    **encadeada** nela (sucesso → sucesso; falha → falha). Hoje ela conclui na hora, o que agora daria uma
    durabilidade prematura. Sem force em voo, a regra é a de hoje (`onCheckpointCoalesced`).
  - `Shutdown` (close) continua inline. O force final do `close()` cobre tudo. Um ticket ainda em voo no pool só
    toca o shard, que vive enquanto o volume estiver aberto.
- **Configuração (registro de volumes):** `NgrrdBlob.Builder.checkpointForceExecutor(Executor)`, no mesmo padrão de
  `qualityListener`/`volumeMetricsListener` (`oss/blob/NgrrdBlob.java:78-89`), propagado ao writer por
  `Ngrrd.buildHandle` (`oss/Ngrrd.java:270-301`). `null` (padrão) = inline. Fica fora de `BlobVolumeConfig`, para
  preservar a idempotência por nome.
- **Medida por checkpoint:** `NgrrdHandle` ganha
  ```java
  /** Como checkpointAsync(), com os tempos medidos. Default: sem medida (zeros). */
  default CompletableFuture<CheckpointTiming> checkpointAsyncTimed() {
      return checkpointAsync().thenApply(v -> CheckpointTiming.NONE);
  }
  record CheckpointTiming(long queueWaitNanos, long forceNanos, boolean coalesced) {
      static final CheckpointTiming NONE = new CheckpointTiming(0, 0, true);
  }
  ```
  - `queueWaitNanos` = do enfileiramento do Sync até o início do force. Inclui a fila FIFO da série, a fila do
    writer pool e a fila do pool de force.
  - `forceNanos` = duração do force.
  - `Ngrrd.DefaultHandle` implementa de verdade.

**D.2 Nó: pool `ngrrd.checkpoint.threads`.**
- **Config:** `ngrrd.checkpoint.threads` (int ≥ 0, padrão **0** = inline, o comportamento de hoje). Vale para
  **todo** checkpoint do nó (local, `CHECKPOINT`/`FLUSH` remoto e migração), inclusive com `enabled: false`.
- **Pool:** `NgrrdStorageNode` cria um `ThreadPoolExecutor` fixo `ngrrd-checkpoint-force-N` (daemon, fila sem
  limite: a entrada já é limitada por `maxInFlight` e pela concorrência de RPC) e passa ao `NgrrdBlob.Builder`.
- **Ordem de encerramento:** `LocalCheckpointer` → handlers → `registry.close()` → `forcePool.shutdown()` +
  `awaitTermination(5 s)` → volume. Os forces em voo terminam antes de o volume desmapear os shards.
- **Recomendação na doc:** começar com `threads = min(8, nCPU/4)` e `maxInFlight ≥ threads`.

**D.3 Índice incremental de séries sujas** (`cl/node/SeriesHandleRegistry.java`).
- **Estrutura:** `Set<String> dirtyIndex = ConcurrentHashMap.newKeySet()`, mais o campo `boolean indexed` em
  `HandleEntry`, lido e escrito só sob `entry.lock`.
- **`SeriesAccess.recordWrite()`** (sob lock): `writeSeq++`; se `!entry.indexed`, faz `indexed = true` e
  `dirtyIndex.add(key)`.
- **`dirtySeries()`** passa a devolver um instantâneo de `dirtyIndex`, um **superconjunto** das sujas.
- **Poda preguiçosa:** feita pelo próprio `tryCheckpointAsync` (sob `tryLock`):
  - sem entrada corrente (série fechada ou ausente): `dirtyIndex.remove(key)` e, logo depois, recheca
    `entries.get(key)`. Se uma entrada nova já existir com `indexed == true`, devolve a chave ao índice. Uma entrada
    nova que se indexar depois da rechecagem faz o próprio `add`, então nada se perde;
  - se está limpa (`!dirty()`), `indexed = false` e `dirtyIndex.remove(key)`;
  - `BUSY` não poda.
- **Por que nunca podar em `markCheckpointed`:** ele roda fora do lock, na thread do writer, e perderia uma escrita
  concorrente. Os caminhos de fechamento (`close`, `discard`, `closeIdle`, `evict`, `closeForDeletion`,
  `markMigrating`) também **não** removem do índice: uma entrada nova da mesma chave pode já ter se indexado. O ciclo
  seguinte poda.
- **`dirtyCount()`** passa a ser `dirtyIndex.size()`, um limite superior que fica exato logo depois de cada ciclo.
  A doc de `localCheckpoint.dirtySeries` muda de acordo.
- **Memória:** uma entrada por série escrita desde o último ciclo. No pior caso, é o número de séries abertas.

**D.4 `spreadFraction`.** `ngrrd.checkpoint.spreadFraction` (double em (0, 1], padrão **0,8**, o valor de hoje)
substitui a constante `SPREAD_FRACTION`. Fora da faixa, a subida falha com uma mensagem clara.

**D.5 Métricas** (`lifecycleMetrics`, chaves `localCheckpoint.*`, medidas só nos checkpoints disparados pelo
`LocalCheckpointer` via `checkpointAsyncTimed()`):
- `localCheckpoint.queueWaitMsP99` e `localCheckpoint.queueWaitMsMax`;
- `localCheckpoint.forceMsP99` e `localCheckpoint.forceMsMax`;
- `localCheckpoint.coalesced`.

Os dois histogramas usam `LatencyHistogram`, com o máximo **da janela** (item F.1). O `NGRRD_NODE_STATUS` ganha
`lcQwP99=`/`lcForceP99=`.

### 5.3 `LocalCheckpointSettings`
O record ganha `threads` e `spreadFraction`. O construtor de 3 argumentos continua (`threads=0`, `spread=0,8`). O
`StorageNodeConfig` segue o padrão de compatibilidade de construtores que ele já usa.

### 5.4 Contrato e compatibilidade
- Mudança interna ao nó, com config nova cujos padrões preservam o comportamento de hoje.

## 6. Item E — TTL de ociosidade por série

### 6.1 Problema
`handleIdleTtl` (padrão 15 min, `cl/node/StorageNodeConfig.java:1095`) é global. Uma série escrita no ritmo do
`baseStepSec` (900 s) fica ociosa por exatamente um passo e pode ser fechada (checkpoint + close, na thread de
status, D8) logo antes da próxima escrita, que a reabre pela autocura. Esse churn se repete a cada passo, para cada
série dessa definição.

### 6.2 Desenho
- **Config:** `ngrrd.handleIdleTtlStepFactor` (int ≥ 0, padrão **2**). `0` = comportamento de hoje (só
  `handleIdleTtl`).
- **TTL efetivo por entrada:** `max(handleIdleTtl, k × baseStepSec)`.
  - Calculado ao abrir (`open`) e ao reabrir (`reopenIfKnown`) e guardado em `HandleEntry.idleTtlMs`.
  - O `baseStepSec` vem de `spec.time.baseStepSec` (`oss/definition/TimeSpec.java:23`).
  - O parse acontece **uma vez por hash** de definição: `DefinitionRecord` ganha `int baseStepSec`, preenchido em
    `cacheDefinition` (`cl/node/SeriesHandleRegistry.java:819-823`).
- **`closeIdle()`** (`:616-644`) passa a comparar com `entry.idleTtlMs` em vez de `idleTtl`. O despejo por
  `maxOpenHandles` não muda: o teto continua valendo.
- **Métrica:** `lifecycleMetrics.handles.idleTtlExtended` = número de entradas abertas cujo TTL efetivo é maior que o
  global. É um contador mantido na abertura e no fechamento, sem varredura.

### 6.3 Contrato e compatibilidade
- Só no nó.
- **Muda o comportamento padrão** de uma forma: séries com `baseStepSec > handleIdleTtl / 2` (> 450 s com os padrões)
  ficam abertas por mais tempo. O efeito é mais handles abertos, limitados por `maxOpenHandles`. Ver a seção 11,
  decisão 6, e a seção 12, Q2.
- Rollback: `handleIdleTtlStepFactor: 0`.

### 6.4 Testes
- `SeriesHandleRegistryTest`:
  - `ttlEfetivoUsaPassoDaDefinicao` (passo de 900 s, TTL de 15 min, k=2: não fecha com 16 min, fecha com 31 min);
  - `fatorZeroMantemTtlGlobal`;
  - `definicaoParseadaUmaVezPorHash`.
- `StorageNodeConfigTest`: parse e validação.

### 6.5 Riscos
- **Mais handles abertos.** Cada handle aberto custa um writer e um canal, ambos leves. O teto continua sendo
  `maxOpenHandles`.
- **Nós com `maxOpenHandles` justo.** Mais pressão de LRU. A doc pede para conferir `openHandles` contra
  `maxOpenHandles` antes do upgrade.

e `:826`. As causas reais estão em D3.

**Desenho:**
- `SeriesHandleRegistry` ganha `NotOpenCause notOpenCause(String key)`, com
  `enum NotOpenCause {RESTART, CLIENT_CLOSED, MIGRATED, REOPEN_FAILED, FROZEN}`. A decisão segue esta ordem:
  1. `isMigrationFrozen(key)` → `FROZEN`;
  2. `forgotten.contains(key)` ou `recentlyMigratedIn.contains(key)` → `MIGRATED`;
  3. `recentlyClosedByClient.contains(key)` → `CLIENT_CLOSED`;
  4. `hashBySeriesKey.containsKey(key)` (definição conhecida, a reabertura falhou) → `REOPEN_FAILED`;
  5. senão → `RESTART` (definição desconhecida neste processo: reinício do nó ou série nunca aberta aqui).
- **Conjuntos limitados:**
  - `recentlyClosedByClient` e `recentlyMigratedIn` são LRU (`LinkedHashMap` com `accessOrder`, sob um lock próprio)
    com teto de **65.536** chaves cada (constante);
  - são preenchidos em `close(key)` e por um `noteMigratedIn(key)` novo, chamado em
    `cl/rebalance/MigrationExecutor.java:814` (`MIGRATE_COMMIT` no destino);
  - `open(key)` remove a chave dos dois;
  - ao estourar o teto, a causa cai em `RESTART`, e a doc avisa que a classificação é aproximada;
  - os conjuntos substituem os "marcadores por série sem limite" que a #174 proibiu.
- **Contagem:** os quatro pontos de `recordError(NOT_OPEN)` passam a chamar `recordNotOpen(key)`, que também
  incrementa `notOpen.<cause>` (chaves `notOpen.restart`, `notOpen.clientClosed`, `notOpen.migrated`,
  `notOpen.reopenFailed`, `notOpen.frozen` em `lifecycleMetrics`). `errorsByStatus.NOT_OPEN` continua sendo o total,
  sem obsolescência.
- **Churn de handles** (`lifecycleMetrics`):
  - `handles.idleClosed` (incrementado em `closeIdle`);
  - `handles.evicted` (em `evictIfOverLimit`);
  - `handles.selfHealed` (quando `reopenIfKnown` reabre de fato).

  São esses contadores que mostram o custo do TTL curto (item E), e não o `NOT_OPEN`.
- **Relação com a 8.16:** com a R5(a), a definição passa a ser persistida, e `RESTART` deve ir a ~0 depois do
  upgrade. As chaves continuam.

## 11. Decisões tomadas na spec

1. **Pool de checkpoint = só o force sai do writer (D6).** O checkpoint inteiro não pode sair sem quebrar a ordem FIFO
   da série. A fase B destacada também é a base do force agrupado por shard (R7(b)).
2. **`threads: 0` como padrão.** Preserva o comportamento de hoje. O ganho vem só com opt-in, como foi com o
   checkpoint local da 8.14.
3. **As métricas `localCheckpoint.queueWaitMs`/`forceMs` medem só o checkpoint local**, via `checkpointAsyncTimed()`.
   Os nomes do roadmap ficam com escopo honesto. O checkpoint remoto já tem `checkpointLatency`.
4. **O índice de sujas é um superconjunto com poda preguiçosa** no ciclo, sob `tryLock`. A alternativa (poda em
   `markCheckpointed`) perde escrita concorrente. `dirtySeries` vira limite superior.
5. **`release` não manda `CLOSE` ao nó por padrão.** O `CLOSE` descarta a definição no nó e causaria `NOT_OPEN` no
   cliente que assume a série. Também não faz checkpoint por padrão, para ter a mesma garantia de uma marca (ACK sem
   fsync). As duas coisas são opções.
6. **`handleIdleTtlStepFactor = 2` como padrão**, contrariando a regra de "padrão preserva o comportamento". É a
   correção de um defeito confirmado (churn a cada passo), o efeito é limitado por `maxOpenHandles` e `0` restaura o
   comportamento de hoje. Precisa de aprovação (Q2).
7. **O passo usado no TTL é `spec.time.baseStepSec`.** É a cadência de escrita esperada. O `heartbeatSec` por DS
   seria mais preciso, mas varia entre DSs.
8. **`NOT_OPEN` por causa usa LRUs limitados** (65.536) e não marcadores por série. As causas do roadmap viraram
   `restart`, `clientClosed`, `migrated`, `reopenFailed` e `frozen` (D3). `idleClose` e `evicted` viram contadores
   de churn, porque não geram `NOT_OPEN`.
9. **`fillOfDeclaredCapacity = (live + reserved) / declarada`**, a mesma conta da recusa a 95%, para que o alerta e a
   recusa falem a mesma língua.
10. **Os limiares 80/90/95 são só documentação e log** (`NGRRD_VOLUME_FILL`). Nenhuma decisão de placement muda nesta
    release.
11. **Máximo "por janela" = 60 s sobre o reservatório.** Uma janela por tempo, e não por número de amostras, porque
    comandos raros reteriam um pico por horas.
12. **Interner com teto fixo de 4.096 e sem chave de config.** O caso real tem 10 definições. O teto só protege
    contra abuso.
13. **Obsolescência:** `rpcLatency` agregado e `seriesDelete.<STATUS>` continuam iguais na 8.15.x e saem numa minor
    ≥ 8.16. `errorsByStatus.NOT_OPEN` **não** é obsoleto (vira o total das causas).
14. **Rota com dono por identidade de handle (`holders`).** Não depende de consultar o `SeriesHandleCache` dentro do
    dispatcher. Evita acoplamento e corrida com `open()`.
15. **Classificação de risco das tarefas** (regra 4 do processo): concorrência, persistência ou contrato → Refuter.
    Docs e métricas sem concorrência → conferência do orquestrador. O Refuter de branch roda antes do merge.

## 13. Fora de escopo (follow-ups registrados)

- `DefaultNgrrdClusterClient.open()` faz um `resolveExistingAtLeader` remoto a cada `open()` de um handle já em cache
  (`:331-337`). É um custo por chamada em clientes que reabrem com frequência.

- `SeriesLifecycleService.metrics()` itera o journal e faz I/O (`exists`/`openSeries`) por série em quarentena a cada
  tick (`cl/node/SeriesLifecycleService.java:44-63`).
- R7(b): force agrupado por shard (8.19), que reaproveita o `ForceTicket`.
